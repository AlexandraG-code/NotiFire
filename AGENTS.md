# NotiFire

Этот файл — единственный источник правил для всех агентов (Claude, Codex, Cursor, Copilot, DeepSeek, GLM). `CLAUDE.md` только подключает его. Правила меняем здесь.

Чат для отправки и получения текстовых сообщений через GREEN-API (тестовое задание, см. `src/task.txt`).
Пишем как кусок коммерческого проекта: аккуратно, расширяемо, без «одноразового» кода.

## Стек

React 19, TypeScript, Vite, antd 6, zustand, axios, react-router-dom, i18next, motion (анимации), sass. Менеджер пакетов — yarn. Не добавлять redux/RTK Query и другие менеджеры состояния.

## Архитектура

Feature-Sliced Design, алиасы `@app @pages @widgets @features @entities @shared`.
Слайс: `api/` (запросы), `model/` (стор, типы), `ui/` (компоненты), `index.ts` — публичный API.
Импорты между слайсами — только через `index.ts`; вышележащий слой импортирует нижележащий, не наоборот.

## Правила кода

- **Типы отдельно от логики.** Доменные и общие типы (`Chat`, `Message`, пропсы компонентов, параметры функций) — в `types.ts`, enum — в `enums.ts`, константы — в `constants.ts` рядом. Исключение — типы самого стора (`State` и `Actions`): они нужны только ему, поэтому лежат в файле стора над хуком и не экспортируются. Не смешивать типы с функциями и компонентами в других случаях.
- **Один файл — одна ответственность.** Не сваливать функции, классы и типы в один файл.
- **Один компонент — одна папка.** Если в `ui/` слайса два и больше компонентов, у каждого своя папка `ui/<Компонент>/`: `<Компонент>.tsx`, `<Компонент>.module.scss`, при необходимости `<Компонент>.variables.scss` и `types.ts` с его пропсами. В одном файле один компонент: иконки, элементы списка и подкомпоненты — отдельные папки, а не «вспомогательные» файлы рядом (нельзя `ui/MessengerLogos.tsx` с двумя логотипами или `ChatListItem.tsx` рядом с `ChatSidebar.tsx`). Если компонент в `ui/` один, файлы лежат прямо в `ui/`, а типы его пропсов — в `model/types.ts` слайса; общего `ui/types.ts` на несколько компонентов не заводить. Подкомпонент, который нужен только родителю, импортируется родителем из соседней папки (`../ChatListItem/ChatListItem`), наружу через `index.ts` не экспортируется. То же в `shared/ui`: каждый компонент — своя папка.
- **Файл компонента — только разметка.** В `.tsx` нет констант (тайминги анимации, размеры, тексты бренда, магические числа), типов и логики: константы лежат в `constants.ts` рядом с компонентом, типы — в `types.ts`, вычисления и обработчики длиннее нескольких строк — в хуке или хелпере. Если у компонента есть самостоятельная часть (надпись с анимацией по буквам, элемент списка, иконка, заголовок карточки), это отдельный компонент в своей папке со своими `constants.ts`, `types.ts` и стилями, а родитель его только подключает. Признак того, что пора делить: в компоненте больше одного блока разметки со своей анимацией или своими стилями, либо в начале файла идёт список констант.
- **Не сваливать в `ui/` слайса всё подряд.** В `ui/` фичи или виджета лежат только её собственные компоненты. Универсальный компонент, который не принадлежит фиче (например, поле номера), выносится в `shared/ui` (поля форм — в `shared/ui/Form/<Компонент>/`) и делается управляемым (`value` и `onChange`), а не привязанным к именам полей конкретной формы. Типы разделяются по назначению: пропсы компонентов — в `model/types.ts` слайса (отдельного `ui/types.ts` не заводить), значения форм и доменные типы — в `model/types.ts`. Тексты универсальных компонентов живут в общем пространстве `common`, а не в страничном.
- **Мелкие утилиты не выносить в отдельные файлы.** Небольшие функции (до ~10 строк, нужные только слайсу: форматирование, проверки, обёртки над библиотечными вызовами) собираются в один хук слайса `use<Слайс>Helpers` (например, `features/CreateChat/model/useCreateChatHelpers.ts`), который возвращает объект с функциями: `return { buildPhone, isPhoneValid }`. Внутри хука функции оборачиваются в `useCallback`, у каждой свой JSDoc. Отдельный файл заводится только для крупной или переиспользуемой за пределами слайса логики. Хук вызывать можно только в компоненте, поэтому хелперы, нужные стору или другому коду вне React, лежат обычными экспортируемыми функциями в `model/<слайс>.helpers.ts` (например, `auth.helpers.ts`). Вспомогательных функций в файле стора быть не должно: в нём только типы, начальное состояние и сам стор.
- **Страницы — тонкие оболочки, вёрстка в раскладках.** Раскладки (карточка по центру, две панели и т.п.) лежат в `shared/ui/Layout/<Название>Layout`, принимают содержимое слотами через пропсы и ничего не знают о фичах. Страница только собирает раскладку из виджетов и фич и держит логику уровня страницы (доступ, запуск опроса, выбор экрана). Виджет не импортирует другой виджет: их сочетает страница через слоты (`<ChatSidebar footer={<SettingsMenu />} />`). Блок, объединяющий несколько фич (меню настроек: тема, язык, выход), — отдельный виджет в `widgets/`. Слайсы переключателей называются `<Что>Switcher` (`ThemeSwitcher`, `LanguageSwitcher`).
- **Никаких inline-типов** в сигнатурах (`options: { a?: X }`). Завести именованный `interface`/`type` и использовать его.
- **Никаких строковых литералов-значений** (имена методов API, маршруты, статусы, состояния, HTTP-методы). Только `enum` (разрешены, `erasableSyntaxOnly` выключен) или именованная константа. Исключение: тексты для пользователя.
- **Конфигурация — только через runtime-конфиг** `env-config.ts` в корне (`window._env_`, файл в .gitignore, шаблон — `env-config.ts.sample`). Новые параметры добавлять в sample, в тип `Window['_env_']` (`src/vite-global.d.ts`) и в таблицу параметров README, читать напрямую через `window._env_`. Файл `env-config.ts` в код не импортируется: `vite.config.ts` отдаёт его как обычный скрипт `env-config.js`, подключённый в `index.html` до модулей (иначе при сборке модули могли бы выполниться раньше конфига). Маршрутизация — `createHashRouter` и относительный `base`, чтобы сборка работала на статическом хостинге в любой папке. **Всё, что связано с API** (таймауты, число попыток и паузы между ними, интервалы опроса и перепроверки, размер выборки истории, адрес хоста), — только в `env-config`, а не константой в коде. Параметры самого приложения (размеры, отступы, тайминги анимации) остаются именованными константами рядом с компонентом. `import.meta.env` и `.env` не использовать. Никаких захардкоженных URL и «магических» чисел — выносить в константы.
- **JSDoc** — на каждом компоненте, хуке, сервисе и функции с аргументами. Формат: описание в 1–2 строки, затем `@param {Тип} имя - описание` на каждый проп или аргумент (необязательные — `[имя]`), `@returns {Тип} описание` (у компонента `{JSX.Element}`) и `@throws`, если функция бросает. Для сторов — только описание. JSDoc не писать там, где он повторяет имя: enum, константы, простые типы.
- **Описание полей интерфейса — один блок над ним.** Если поля интерфейса (или типа-объекта) нужно пояснить, пишется один JSDoc-блок над сущностью: первая строка — что это, дальше `@property {Тип} имя - описание` на **каждое** поле (необязательные в виде `[имя]`, функции как `{Function}`). Комментарии над отдельными полями внутри интерфейса не писать. Длина строки до 120 символов, длинное описание переносится на следующую строку. Для интерфейсов, где поля и так очевидны, блок не нужен.- Секреты (`apiTokenInstance`) не логировать, не коммитить, не вставлять в код и тексты ошибок. Тексты сообщений рендерить как обычный текст, без `dangerouslySetInnerHTML`.
- **Ошибки — через стор уведомлений.** Действия сторов, которые ходят в API, оборачиваются в `runAsyncAction` (`@shared/lib`): он единственный ловит ошибку и передаёт её в стор уведомлений `useNotificationStore` (`notifyError`), поэтому в сторах и компонентах отдельный `try/catch` ради показа ошибки не нужен. Свой текст ошибки задаётся параметром `describeError` в самом сторе (например, `describeLoginError` в `useAuthStore`). Единственное место, где ошибка показывается пользователю, — `src/app/providers/ErrorNotifier.tsx`: он читает очередь из стора уведомлений. Вызывать `notification.error` и `message.error` напрямую в компонентах и сторах нельзя; чтобы сменить способ показа (окно ошибок и т.п.), правится только `ErrorNotifier`.
- **Порядок в теле компонента и хука.** Блоки идут строго в таком порядке, между блоками одна пустая строка, внутри блока пустых строк нет:
    1. вызовы сторов (`useXStore(selector)`);
    2. состояния (`useState`, `useReducer`);
    3. библиотечные хуки (`useNavigate`, `useParams`, `useRef`, `Form.useForm`, `App.useApp` и т.п.);
    4. наши хуки (`useSendMessage`, `useThemeToggle` и т.п.);
    5. вычисляемые значения из пропсов и хуков;
    6. `useMemo` — все подряд;
    7. `useCallback` — все подряд;
    8. `useEffect` и `useLayoutEffect` — все подряд;
    9. обработчики и прочие функции, затем `return`.

    Хуки одной группы идут подряд, без пустых строк между ними, а группы нельзя дробить и перемешивать: все сторы вместе наверху, потом все состояния, потом библиотечные хуки, потом наши (даже если их несколько, они один блок).

    Если селектор стора зависит от библиотечного хука (например, от `useParams`), брать из стора весь срез, а нужный элемент находить в блоке вычисляемых значений.

- **API по слайсам.** В `shared/api` лежит только общий клиент: axios-инстанс, `callGreenApi`, сборка URL, `GreenApiCredentials`, хелперы `chatId`, которыми пользуются несколько слайсов. Сервисы конкретных методов, их типы и enum лежат в папке `api/` слайса, который ими пользуется: `<имя>.service.ts`, `types.ts`, `enums.ts` (например, `features/SendMessage/api`). Общий объект со всеми методами в `shared` не заводить.
- **Сервис — только вызовы API.** Сервис (`<имя>.service.ts` в `api/` слайса) — объект с методами, каждый метод делает один запрос и возвращает данные: `export const SendMessageService = { async sendMessage(creds, params) { return callGreenApi(...) } }`. В сервисе нет проверок результата, `if`, `try/catch`, `throw`, подбора текстов ошибок, уведомлений, работы со сторами и преобразования данных. Всё это — в сторе (или в хуке фичи): стор вызывает сервис, проверяет ответ, решает, что считать ошибкой, и выбирает текст для пользователя. Чужая логика «просочилась» в сервис — вынести её в стор.
- Сервисы API принимают креды аргументом, глобального состояния не читают.
- Стиль: prettier (табы, без `;`, одинарные кавычки), `import type` для типов (`verbatimModuleSyntax`).
- **Цвета и размеры — только из темы.** Токены в `src/shared/theme`: у каждого оформления (скина: `maxLightTokens.ts`, `maxDarkTokens.ts`, `telegramLightTokens.ts`, `telegramDarkTokens.ts`) свой набор, тип `ThemeTokens`, выбор по паре `Skin` + `ThemeMode` в `themes.ts`; в CSS — переменные `var(--color-*)`, в antd — токены через `getAntdTheme`. Хекс-цвета в компонентах и стилях не писать; новый цвет — сначала во все наборы токенов (все скины, светлая и тёмная тема), иначе тема где-то останется без значения. Бренд-логотипы (MAX, Telegram, NotiFire) — исключение: их цвета остаются в самой иконке. Стили компонентов — SCSS Modules (`*.module.scss`), см. правило про стили.
- **Стили: SCSS, rem и переменные.** Стили компонентов — `*.module.scss`, подключают общие переменные через `@use '@shared/styles' as *;` (`src/shared/styles`: функция `rem()`, шкалы отступов, скруглений, размеров шрифта, размеры блоков, миксины). Размеры, отступы и шрифты — в `rem` через `rem(px)` или готовые переменные; `px` допустим только для границ в `1px` и для брейкпоинтов. Голых чисел в правилах нет: число берётся из общих переменных, а если оно нужно одному компоненту — выносится в его партиал `<Компонент>.variables.scss` с комментарием, откуда оно. Узкое окно — только миксином `@include narrow`, порог 900px записан один раз в `shared/styles/variables.scss`.
- **Переменные SCSS не держать в одном файле со стилями.** Общие переменные, функции и миксины живут в `src/shared/styles`. Переменные, нужные одному компоненту, выносятся в соседний партиал `<Компонент>.variables.scss` (например, `MessageBubble.variables.scss`) и подключаются в стилях через `@use './<Компонент>.variables' as *;`. В самом `*.module.scss` объявлений `$переменных` быть не должно, только их использование.
- **Числа и функции без «магии».** В TS числовой литерал либо выносится в именованную константу с комментарием, что это, либо поясняется комментарием в той же строке (исключения: `0` и очевидные счётчики). Каждая функция уровня модуля, в том числе неэкспортируемая, имеет JSDoc с `@param` и `@returns`; вложенные обработчики внутри компонентов без JSDoc.
- **Фигурные скобки обязательны.** У `if`, `else`, `for`, `while` тело всегда в `{ }` на отдельных строках, даже если оно в одну строку: нельзя писать `if (x) return y`, нужно `if (x) {` и `return y` на следующей строке. Проверяет ESLint (`curly: all`), он же исправляет автоматически (`yarn eslint src --fix`).
- **Тело `useEffect` — вызовы функций, а не логика.** В эффекте допустимы проверка условия, вызов одной именованной функции и возврат очистки (подписка и отписка, остановка опроса). Асинхронные цепочки, `.then`/`.catch`/`try`, циклы и преобразования данных выносятся в именованные функции: в хуке это `useCallback` с JSDoc (в блоке `useCallback`, до эффектов), для самостоятельной логики — функция модуля в своём файле (например, `pollNotifications.ts`). Эффект читается как «при таком изменении вызвать вот это», а сама логика остаётся переиспользуемой.
- **Локализация (i18next): никаких текстов в коде.** Любой текст для пользователя (подписи, плейсхолдеры, `aria-label`, сообщения об ошибках, названия) идёт через i18next; русских и английских строк в коде быть не должно. Переводы лежат в `src/shared/i18n/locales/<страница>/<язык>/<страница>.json`, языки `ru` и `en`, оба файла обязательны. Новое пространство: значение в enum `Namespace`, файлы `en` и `ru` и тип в `types.ts`. В компонентах — `useTranslation(Namespace.X)`, вне React (сторы, хелперы) — `i18n.t('ключ', { ns: Namespace.X })`. Ключи типизированы по русским файлам. **Грузить всё сразу нельзя:** в `init` в `ns` остаётся только `Namespace.Common`, страничные пространства подгружаются при открытии страницы в `lazy` маршрута через `loadNamespaces`, `fallbackLng` не задаётся (иначе грузится второй язык). Даты, время и названия стран форматируются через `Intl` с `i18n.language`, а не с жёстко заданной локалью.
- **Анимации — через `motion`.** Сложные анимации (появление по буквам, сдвиги, раскрытие по ширине) пишутся на `motion/react` (`motion.div`, `AnimatePresence`), а не вручную на таймерах и `requestAnimationFrame`. Простые (hover, цикличное мерцание) — CSS `@keyframes` в модуле стилей. Все длительности, задержки и смещения — именованные константы в `constants.ts` компонента. Движение должно отключаться при `prefers-reduced-motion`: в `motion` — `MotionConfig reducedMotion="user"`, в CSS — `@media (prefers-reduced-motion: reduce)`.
- **Скины мессенджеров.** Выбор мессенджера (`Skin`: MAX, Telegram) хранится в `useSkinStore` (фича `MessengerSelect`) и вместе с режимом темы определяет токены и конфиг antd. Новый скин — значение `Skin`, набор токенов (светлый и тёмный) и запись в `themeTokens`; в компонентах скин не проверяется, внешний вид меняется только токенами.
- **Фоновые и необязательные запросы не мешают пользователю.** Проверки-подсказки (настройки инстанса, подгрузка истории и профиля) не показывают ошибку, если это не результат действия пользователя: ошибка идёт в консоль (`runAsyncAction(..., { silent: true })`). Запросы с лимитами API (например, `getSettings`) защищаются от повторного вызова, пока предыдущий не завершился.
- **В git не попадают** `src/task.txt` (условия задания, держим локально), `env-config.ts`, ключи и токены. Реальные `idInstance` и `apiTokenInstance` в код, README, коммиты и сообщения не вставлять; в примерах — заглушки.
- **Тесты.** Юнит- и компонентные тесты (Vitest + Testing Library) лежат рядом с кодом: `<имя>.test.ts` или `<имя>.test.tsx`. Сквозные (Playwright) — в `e2e/`. Новая фича или исправление ошибки идут с тестом: хотя бы на главный сценарий и на ошибку. Проверяется поведение (что видит и получает пользователь, что попало в стор), а не внутренности. Запросы к GREEN-API в тестах подменяются (`vi.mock` сервиса в юнит-тестах, `mockGreenApi` в e2e); настоящие `idInstance` и токены в тесты не вставлять. Тексты ищутся по-русски: тесты идут при русском языке интерфейса. Перед коммитом: `yarn test`; если менялись экраны или потоки — `yarn e2e`. CI запускает всё и блокирует выкладку при падении.
- Файлы `.gitkeep` не заводить.

## Проверка перед коммитом

`yarn tsc -b && yarn lint`, затем `yarn format`. Один коммит на задачу.

## Комитет агентов

Защищённое (конфиги сборки, `.env*`, CI) правит только оркестратор. Чужой код проверяется `validator` перед записью в проект.
